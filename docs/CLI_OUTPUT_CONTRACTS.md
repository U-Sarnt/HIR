# CLI Output Contracts

HIR phase 5 formalizes the public CLI output rules for both human use and automation. This document is the contract for `stdout`, `stderr`, exit codes, and JSON exports.

## Scope

The contract applies to the validated public commands:

- `hir ping`
- `hir traceroute`
- `hir arp-scan`
- `hir report-export`

## stdout and stderr

HIR now follows a strict split between command results and operational messaging.

### stdout

`stdout` is reserved for the primary command result only.

- `console` format commands print the rendered report body to `stdout`
- `json` exports print only the generated JSON file path to `stdout`
- `html` exports print only the generated HTML file path to `stdout`
- `--help` output is written to `stdout`

### stderr

`stderr` is reserved for non-result messaging.

- usage errors
- invalid arguments
- runtime failures
- operational failures such as missing privileges or unsupported report input

HIR does not print warnings, banners, or progress text to `stdout` when the command result is meant to be machine-consumable.

## Exit Codes

HIR uses stable process exit codes:

- `0`: success
- `1`: operational/runtime error
- `2`: usage error or invalid CLI arguments

These codes are centralized in [src/hir/cli_contracts.py](../src/hir/cli_contracts.py).

## JSON Contract

All JSON generated by the public CLI is now written as a versioned top-level document:

```json
{
  "schema": "hir.report",
  "schema_version": 1,
  "report_type": "ping",
  "report": {
    "host": "1.1.1.1",
    "count": 4,
    "timeout": 2,
    "rtt_ms": [10.1, 12.3],
    "received": 2,
    "min_ms": 10.1,
    "avg_ms": 11.2,
    "max_ms": 12.3
  }
}
```

Top-level keys are stable and ordered as:

1. `schema`
2. `schema_version`
3. `report_type`
4. `report`

### Supported `report_type` values

- `ping`
- `traceroute`
- `arp-scan`

### Report payload shape

`report` contains the typed payload for the command.

- `ping` keeps a flat object with packet counts and RTT summary fields
- `traceroute` uses `hops` as an array of objects with `hop`, `ip`, and `rtt_ms`
- `arp-scan` uses `devices` as an array of objects with `ip`, `mac`, `vendor`, and `os`

### Schema versioning

- Current schema: `hir.report`
- Current version: `1`
- Future incompatible changes must increment `schema_version`

## Compatibility Notes

HIR keeps backward compatibility when reading previously exported traceroute and ARP JSON files:

- `hir report-export` accepts both legacy raw JSON payloads and the new versioned document
- legacy traceroute hop arrays like `[1, "192.168.1.1", 1.23]` are still accepted on read

New JSON written by the CLI always uses the versioned document shape.

## Human Usage Examples

```bash
hir ping 1.1.1.1
hir traceroute example.com --format html
sudo "$(command -v hir)" arp-scan 192.168.1.0/24 --format json
```

## Automation Examples

Capture only the exported JSON path:

```bash
json_path="$(hir ping 1.1.1.1 --format json)"
```

Fail fast on usage or runtime problems:

```bash
if ! json_path="$(hir traceroute example.com --format json 2>hir.err)"; then
  status=$?
  cat hir.err >&2
  exit "$status"
fi
```

Read the stable schema fields:

```bash
python3 - <<'PY'
import json
from pathlib import Path

path = Path("results/json/ping_1_1_1_1_01.json")
document = json.loads(path.read_text(encoding="utf-8"))
assert document["schema"] == "hir.report"
assert document["schema_version"] == 1
print(document["report_type"])
PY
```
